# 0018: A grounded assistant: retrieval for explanation, validated tools for facts

**Context.** A visitor evaluating Clearline should be able to question the design, the decisions and the evidence, and later the demo data. A generic chatbot would invent answers, and a model that "answers" a total from retrieved prose can be fluently wrong.

**Decision.** Two separate evidence paths with an explicit router (`src/assistant/router.ts`):
1. **Explanation** (architecture, decisions, capabilities, security): vector retrieval over an approved, versioned corpus. Chunks carry source, heading, content hash and an access class, and the class filter runs in SQL before any text reaches an answer. A model, when configured, may only phrase an answer from the retrieved sources and must cite them; without a model the answer is extractive and labelled as such.
2. **Facts** (current numbers, comparisons, reconciliation and run status): never from retrieval. Computed by narrow data tools (`src/assistant/tools.ts`) with strict argument schemas: a metric's current value, a metric over a period (optionally grouped), a two-period comparison, data quality, reconciliation status, and for signed-in users recent runs and run insights. The measures are the active contract's own declared metrics (`content/data-tools.json` only names date fields and dimensions per entity). SQL is generated from validated values (enumerated ids, calendar dates, bounded windows), never written by a model, and runs through the existing governed flow: a proposal, then an explicit execution that re-validates for the caller's role under the current field policy on the read-only query role, with timeouts, row caps and audit. Each invocation is persisted as evidence (`assistant.tool_calls`: operation, definition, window, execution id, aggregate result, qualifications, limitations) and linked from the answer; answers are rendered from the tool result by templates, so a language model never writes a figure. A model is used at most to choose among the same tools when the rules cannot map a question.

**Identity for data.** Signed-in questions run as the caller (own tenant, own role, own field restrictions); the assistant never accepts a claimed identity. Anonymous questions run as a fixed `public-assistant` identity with the least-privileged role on one tenant that an operator names in `ASSISTANT_PUBLIC_DATA_TENANT` (synthetic demo data); unset means anonymous visitors get no data answers. The signed-in-only tools are refused for that identity, and the request-bound tenant scope makes the data layer refuse any other tenant whatever the arguments say. Data questions have their own, tighter rate limit.

**Failure behaviour.** A tool failure (validation, permission, timeout, database) produces an answer that says the calculation could not be completed and contains no figure; a document is never substituted for a number. Interpretation questions ("is this unusual?") use the recorded run insights, which are statistical deviations with stated methods and limitations; the answer separates what was measured from hypotheses worth investigating, and states that a cause is not established. Anonymous visitors have no runs to interpret and are pointed to sign-in.

**Vector store.** pgvector inside the existing PostgreSQL (schema `assistant`), built into the database image (`db/Dockerfile`) so there is no second database and the index shares backups. Embeddings come from a small local model (`Xenova/all-MiniLM-L6-v2`, 384 dimensions, run in-process, baked into the image), so no corpus text leaves the machine and no paid key is needed. The index records the embedding provider, model and dimension and refuses to mix vectors; changing the model requires an explicit rebuild.

**Alternatives.** A dedicated vector database (another system to run, secure and back up); hosted embeddings (a third-party dependency and key for a small public corpus); full-text search only (does not meet semantic retrieval); a retrieval-only design that also answers data questions (rejected: it would present prose as data).

**Consequences.** Retrieval quality is limited by a small model; it is measured on a version-controlled evaluation set (`docs/assistant-evaluation.md`) rather than claimed. Retrieval has no tools and the data tools take validated arguments only (never SQL, tenant, role or identity), so prompt injection in retrieved text or in a question cannot cause an action beyond the fixed, authorized operations; output is rendered as text and navigation targets come from a fixed destination table. Public requests are rate limited per client and globally (in memory, per process). Conversations are not stored on the server. The index must be rebuilt after content changes (`npm run assistant:index`, or `docker compose run --rm index`).

**Costs of the data tools.** A fixed set of operations: a question outside it is declined with the supported metrics listed, and free-form analysis stays in the query workspace. Evidence rows accumulate (pruned after 30 days). Period queries need a date field per entity in `content/data-tools.json`.

**Revisit when** recall on the evaluation set is too low, the corpus outgrows pgvector, per-tenant private corpora are needed, or users need analytical questions beyond the fixed operations (a governed text-to-SQL path already exists in the query workspace).
